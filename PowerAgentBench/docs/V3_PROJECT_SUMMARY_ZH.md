# v3 阶段工作总结（截至 2026-10-02）

> 面向课程汇报和后续论文写作的中文总结。详细数字以 [V3_DEV_PILOT_RESULT.md](V3_DEV_PILOT_RESULT.md) 为准；Dev Pilot 是开发诊断，不是论文 Test 结论。

## 1. 研究问题

大模型代理在 IEEE 33 节点配网里用储能（BESS）调节电压越限时：

- **验证（V）**：提交前先预览潮流结果，是否提高成功率？
- **恢复（R）**：首次提交失败后允许修正再提交，是否提高成功率？
- **V 与 R 是互补还是重叠？** 这取决于控制结构：有的问题简单调一下就够，有的需要多台储能协调。
- **信息接口（I）**：给模型原始数据还是领域摘要，是否有影响（探索性）。

实验把 I、V、R 各开关一次，共 8 个条件（I0/I1 × V0/V1 × R0/R1）。

## 2. 为什么要做 v3

v2 语料的难度分布没有按“控制结构”分层，Dev 上也有天花板风险。v3（路线 B）按控制结构把场景分成四层：

| 层 | 含义（概括） |
|---|---|
| S1 | 简单，单一动作即可 |
| S2 | 需要一定调节，但不复杂 |
| S3 | 需要多台储能协调 |
| S4 | 最难，协调要求最高 |

每个场景都由评价器离线认证（模板搜索和 witness），保证有可行解，并且分类不依赖任何模型得分。

## 3. 已完成的工作

1. **离线验收（B0–B4 PASS）**：32 个 Dev 场景（S1–S4 各 8 个）、受限预算脚本基线、独立校验。离线基线 `bounded_local` 在 Dev 上的成功数为 S1 8/8、S2 3/8、S3 3/8、S4 0/8。
2. **预登记**：在任何 v3 模型输出之前，固定了范围、对比定义（`dV`、`dR_V0`、`VR`）、天花板规则、协议阻断规则和 smoke 场景。
3. **8 局 smoke**：连通性检查，不计入结论。
4. **256 局 Dev Pilot**：32 个场景 × 8 个条件 × 1 次，模型 DeepSeek-V4.1-Flash（接口标识 `deepseek-flash`），输出上限 16384，推理强度 high。本次运行已计费 ¥7.12，未知用量预留 ¥4.20，合计约 ¥11.3；输入缓存命中率 78.3%。（共用账本整体占用 ¥15.4，包含早期 v2 运行和 smoke。）
5. **后续诊断**：连接层错误、输出截断、32768 输出上限的 4 局小实验（见 §5）。

## 4. 主要结果（Dev Pilot，256 局）

| 条件 | 成功率（全部 32 个场景） |
|---|---|
| 都不加（I0-V0-R0） | 约 22%（7/32） |
| 只加恢复（I0-V0-R1） | 28/32 |
| 只加验证（I0-V1-R0） | 27/32 |
| 两者都加（I0-V1-R1） | 32/32 |

场景配对 bootstrap 的主要对比（MACRO，百分点）：

- 验证 `dV`：**+36.7**，区间 [30.5, 42.2]，四个层都为正。
- 恢复 `dR_V0`：**+60.9**，区间 [43.8, 76.6]。
- 交互 `VR`：**−51.6**，区间 [−71.9, −29.7]。**V 与 R 重叠而不是互补**：有了其中一个，另一个的增益大幅缩小。
- 信息接口 `dI`（探索性）：−2.3，区间 [−6.3, 1.6]，无可辨别的效果。
- 难度随结构升高：不加 V、R 时 S3、S4 几乎全败（0/8～1/8）；只有 V 与 R 同时加，S4 才全部成功。
- 预登记的天花板判定**不成立**，不启用小预算实验。

## 5. 诚实的局限与诊断

- **样本小**：每层只有 8 个场景，区间较宽；每个条件只跑 1 次；只测了一个模型。
- **输出截断**：10 局被截断，其中 9 局集中在 D0007、D0021、D0026；协议阻断的“5%”口径有两种算法：按最终失败是 4.7%（12/256），按出现过解析错误或截断是 11.3%（29/256）。
- **连接层错误**：本次运行 1477 次请求中有 19 个 `ConnectionResetError`/`URLError`，成串出现，间隔约 10 分钟，根因未查（需要检查本机网络，须用户同意）；对结果无影响。
- **32768 输出上限的小实验**：只完成 4 局。全部 35 个请求中只有 1 个达到上限，说明截断减少；但困难局每局 ¥0.15–0.29，约是 Pilot 平均每局（¥0.028）的 5–10 倍，样本太小，不能说成功率提高。
- **方法偏差（须在引用时说明）**：运行中被动中断多次；手工更新运行身份（提交号、源码与价格哈希、预留政策）；节假日按低谷价计费（依据供应商价格页）。详见结果文档第 6 节。

## 6. 下一步：从开发诊断到论文

目标：中文核心期刊。计划为 **96 个 Test 场景（每层 24 个）× 8 个条件 × 3 次重复 = 2304 局**，第二个模型视预算再加。

已完成的准备：

- 预先声明了 [V3_TEST_GENERATION_PROTOCOL](V3_TEST_GENERATION_PROTOCOL.md)（独立 seed 2041、排除 Dev 的 family 与近重复、不足时如实报缺口、不放宽标准）。
- 写了离线脚本 `generate_voltage_structural_test.py`（`scout` / `build-test`）和选择规则的单元测试。
- **S4 可行性扫描正在进行**：Dev 阶段 S4 出产率只有约 1%（1024 个候选中 11 个通过认证），能否凑够 24 个独立 S4 要看扫描结果。

之后的顺序：扫描结果 → 生成 Test → 写 Main 预登记 → 定输出上限（Dev 上小规模验证）→ 冻结 → 跑 Main → 分析与写作。这些步骤中凡会产生模型费用的，都需要先估算并经用户批准；代码里写死的活动上限 ¥22、单局上限 ¥0.20 要先走批准再改。

## 7. 一页话版本

> 在 IEEE 33 节点的 BESS 电压控制任务上，我们按控制结构把场景分成四层，在 32 个 Dev 场景 × 8 个条件的开发实验中发现：验证和恢复都能显著提高大模型的成功率（分别约 +37 和 +61 个百分点），但二者是**重叠**而非互补（交互项约 −52 个百分点）；最难的 S4 需要二者同时具备才能全部成功；信息接口影响不明显。该结果为开发诊断，样本有限、仅测一个模型；下一步将构造 96 个独立 Test 场景并扩大规模，作为论文的正式实验。
