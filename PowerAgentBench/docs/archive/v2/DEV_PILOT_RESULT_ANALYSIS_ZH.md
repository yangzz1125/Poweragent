# Dev Pilot 实验结果分析

## 数据范围与结论边界

只分析公开快照 `research_records/voltage_control/cny_pilot_192/`：24个Dev场景×8个I/V/R条件×1次，共192个episode。原Pilot每请求输出上限4096，reasoning未显式指定；之后的16384/high单例诊断不补入本表。完整任务集无缺失，170成功、22失败，但总成功率88.54%只是运行概览，主结果应按条件比较。

以下是开发集的探索性证据，不是冻结Test或正式跨模型结论。CI来自24个场景的配对/聚类重采样，不把同场景的8个条件当作8个独立样本。未知网络请求的收费保留为预留，不当零也不当确切账单。

## 2. Verification 的证据最强

V1四组共96/96成功，且首次正式submit均成功；V0共74/96成功。按共同场景配对、平均其他因素，V主效应是 **+22.92个百分点**，95% bootstrap CI **[+14.58,+32.29]**。96个成对V比较中22对改善、0对变差，其余不变。

这不意味着初始决策总是正确：96个V1 episode里，**38个第一次preview失败**。真实物理反馈给了Agent在正式submit前修正动作的机会。这是execution-grounded verification比“模型自行确认成功”更有价值的证据。

不要将96/96推广为真实成功概率100%。每个condition只有24个场景；全成功样本的普通bootstrap退化为[1,1]，这种数值不代表没有未知风险。正式Test仍有必要。

## 3. Recovery 主要补偿没有 Verification 的情况

合并两种接口：

| V/R | 成功 |
|---|---:|
| V0-R0 | 27/48（56.25%） |
| V0-R1 | 47/48（97.92%） |
| V1-R0 | 48/48（100%） |
| V1-R1 | 48/48（100%） |

R的平均主效应 **+20.83个百分点**，95%配对bootstrap CI **[+12.50,+29.17]**。但是效果依赖V：V0下恢复明显提高最终成功；V1已经达到天花板，本批数据看不到R的额外终态收益。

R1首次正式submit失败22局，其中21局恢复，条件恢复率 **21/22=95.45%**；最终失败率 **1/22=4.55%**。这些首次失败都发生在V0，不能宣传成“所有类型错误95%都能恢复”，也不能与R0的设计强制终止率作恢复能力比较。两组首次失败者不是人为随机分配的人群，条件恢复率是描述性机制指标，主要比较仍是共同场景上的最终成功差异。

## 4. Interface 尚无稳定正收益

I0总成功86/96，I1为84/96；配对I主效应 **−2.08个百分点**，95% CI **[−7.29,+3.13]**，覆盖0。成对比较中2对改善、4对变差，90对不变。不支持“领域接口提高成功率”的当前结论，也不足以证明领域接口有害。

在V0-R0中：generic欠压7/12、过压7/12；domain欠压9/12、过压4/12。这只是很小的分层线索，不能据此断言domain导致过压控制变差。应审查具体动作与信息表达，不按成绩改Test。

注意：I1是任务语义预处理，不是完整信息等价变换。其成效还受到物理反馈天花板遮蔽：V1里I0/I1都成功，当前case无法进一步区分。

## 5. V 与 R 是部分替代，而非“全开总是最好”

成功率尺度的VR差中差约 **−41.67个百分点**，95% CI **[−58.33,−25.00]**。解释是：R在V0下有约41.67个百分点收益，在V1下本批为0，二者都在纠正错误动作，收益不简单相加。这不说明恢复机制损害性能。

其他交互IV/IR/IVR的CI均覆盖0。多个condition全成功导致logistic分离，不能输出可靠的有限logit系数或捏造p值。使用 `explicit_high_freeze_review/pilot_factorial_rate_contrasts.csv` 的绝对率差/差中差及场景bootstrap更可解释。

## 6. 最值得重视的物理发现：失败主要是过度校正

检查两组V0-R0的21次终态失败：

- 初始欠压，调节后变成过压：8次；
- 初始过压，调节后变成欠压：12次；
- 初始过压，调节后仍过压：1次。

即 **20/21失败是越过目标区间的过度校正**，不是非法动作或明显缺少BESS容量。该统计来自各submit反馈中的剩余欠压/过压节点，未修改评判标准。

这提示Agent可能知道调节方向，但没有掌握合适幅度。Preview与Recovery通过真实反馈弥补幅度估计，而不仅仅是教会它BESS正负号。

## 7. Easy/Medium/Hard 标签未验证为控制难度

I0-V0-R0的成功率：Easy 2/8=25%，Medium 5/8=62.5%，Hard 7/8=87.5%；并未随着标签变难而下降。I1-V0-R0对应4/8、4/8、5/8，也没有清晰的单调关系。

这些标签实际上是初始电压越限幅度的分位档。轻微越限可能更容易被固定幅度动作过度校正，而较大越限恰好能容纳较大动作。这一解释与失败类型一致，但仍需控制余量、局部灵敏度等诊断验证。

建议报告中称 low/medium/high severity，不直接称任务难度，并将幅度选择/安全控制区间作为Dev诊断指标。不要为了获得漂亮的难度曲线重挑Test。

## 8. Reliability–cost：更多工具调用不一定更贵

合并接口、在R0下比较：

| 指标 | V0-R0 | V1-R0 |
|---|---:|---:|
| 成功率 | 56.25% | 100% |
| 平均PF | 2.00 | 3.52 |
| 平均tokens | 15875 | 16063 |
| 平均已知费用（元） | 0.01618 | 0.00814 |

在这批数据中，preview增加约1.52次PF，而总tokens接近、金额反而较低。请求账本提供了两个解释线索：V1-R0平均输出tokens约1051，V0-R0约3076；输入缓存命中也存在差异。输出价格更高，较少输出可能抵消更多输入和交互的成本。

这不证明增加工具永远能省钱。低谷价格、缓存、服务负载和开发中重试政策均影响金额/时延；没有受控实验不能把时延下降归因于V。单独报告PF、input/output/cache tokens、人民币估算和未知预留比只比较总tokens更可靠。

V1时，加入R后成功率仍100%，平均tokens从16063到18813、已知费用从约¥0.00814到¥0.01015。观察上V1-R0较经济，但恢复开关可能改变前期行为且只有单次重复，不能据此永久删除Recovery。

## 9. 解析错误与资源上限仍是混杂因素

28个episode曾有parse_error，23成功、5失败；没有parse_error的164局中147成功、17失败。两类终态失败率约17.9%和10.4%，但条件构成不同、错误可能发生于长轨迹，这只是相关性，不是错误造成的因果增量。

唯一R1最终失败D0015/I1-V0-R1，8次空可见文本都伴随output_tokens=4096。原日志缺provider截断原因，不应简单归类为模型语法能力差。后来16384单例及explicit-high单例都成功，但其单轮实际输出没有超过4096，不能确认扩容导致改善。二者均不纳入这192条统计。

## 总结与下一阶段建议

最稳妥的当前结论是：**在本Dev候选分布中，LLM无物理反馈时容易过度校正；真实preview或失败反馈显著提高观测成功率。领域语义接口尚无稳定收益，V/R存在成功率天花板和部分替代。**

下一阶段应优先：
1. 固定新的16384/high及费用/重试/日志政策，明确与旧Pilot的区别；正式Test另行批准。
2. 保留完整2×2×2，不根据Dev结果删掉I或R；报告零/负结果和成本。
3. 重命名/解释severity档，而非宣称已验证控制难度；把过度校正作为预登记失败类型。
4. 在冻结Test与重复实验中验证V/R、I零收益及成本差异；不将Dev成功率作为论文主表。
5. 保留witness搜索选择偏差、供应商alias漂移、缓存与价格计费限制。

数据来源：Pilot的episodes.csv、events.jsonl、requests.jsonl；main/difficulty/preview统计表；场景配对绝对factorial contrasts。此分析未调用付费API、未修改代码、未更改或重新筛选场景。
